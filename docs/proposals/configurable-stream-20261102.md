## 分阶段执行

### P6-1：配置与预算（本轮）

在现有单文件 agent / 内置 Web UI 上扩展，不引入 Python 运行依赖，不改原生程序：

1. 五档尺寸 + 自定义偶数宽高、目标帧率、四种画面处理方式、raw/H.264/H.265 及目标/最大码率。
2. 系统 NIC 数值型收发速率，精确关联 Npcap GUID；采集端按实际控制连接路由选择，不拿另一块高速网卡凑预算。
3. 使用较慢的实际方向速率，计算 NV12 + 完整 L2 分包开销与工程余量，编码模式仅给均摊估算。
4. “网络预算”“原生实现”“硬件/实际验收”分开；未知速率不当作已支持，未接通配置启动前明确 409。
5. 草稿计算只读；配置编辑防抖、串行请求、旧回复不覆盖新草稿；旧后台缺接口时显示未知，不自动升级。

当前实际路径仍固定 640 raw。416/高清尺寸、缩放和编码选项可保存为草案，但不能运行，
不能只加下拉框就宣称功能完成。UI 和启动后端均落实此边界，低层接口也不静默忽略新参数。

完整 API / 数学定义见 `.agents/skills/virtualcapture/references/stream-config.md`。
Raw 640@240 的净载荷 1.179648Gbps，加入当前 MTU9000 分包完整开销后需求约 1.188392Gbps；
720p@240 约 2.673850Gbps，超过 2.5G；1080p@60 约 1.504017Gbps。均为预算，不是新实测。

### P6-2：可变尺寸 raw 垂直链路（下一阶段）

- 显式会话参数/能力标记、双端共同确认宽高/fps/MTU/像素格式；旧版本不得忽略后仍启动。
- 输出尺寸与桌面源尺寸分离；crop=居中1:1，输出大于源时拒绝；fit=完整等比加黑边；fill=等比铺满再居中裁；stretch=不保比例。
- CPU 参考和 GPU compute 使用明确的整数采样/舍入定义，默认 640 crop 保持已有字节结果；不把 D13 狭窄 UNORM 例外扩散为一般浮点图像处理。
- DDA 限速采用明确的最新帧/跳帧语义，避免 FIFO 排队和重复旧画面制造高 FPS；目标帧率必须真正成为预算可以依赖的上限。
- receiver 动态缓冲、版本化 SHM、Python 镜像、monitor、DShow media type/allocator/重连与验证工具同步升级；会话中不热改尺寸。
- raw 默认路径、其他预设/自定义、黑边/裁切边界/色度对齐做确定性测试；再做隔离回环逐帧哈希与实际虚拟卡取帧，最后才双机。

### P6-3：编解码能力与后端

- 采集端 encoder 与主机 decoder 分别探测。PC1 的 RTX 4070 不能证明 PC2 编码器可用，也不能由安装了 FFmpeg 就推定便携成品具备依赖。
- 优先验证 Windows 原生低延迟后端的实际 MFT/硬件能力；若不满足，再明确评估 SDK/库、许可证、可分发依赖与打包维护成本，不先承诺每块 GPU 支持所有模式。
- H.264/H.265 先独立做编码→解码原型，明确低延迟配置、队列深度、关键帧/恢复流程与错误诊断；压缩仅用于双机链路，主机解码后仍向下游提供 NV12。
- 不静默回退软件/切换 codec/降分辨率或帧率；不支持的组合给出原因。
- 分开验证传输字节完整性、解码有效性/尺寸、画质与丢包后恢复，不以有损前后逐像素相等验收。
