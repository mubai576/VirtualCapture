# 主机控制台（P5，D17）

UI 只在主机提供。主机负责接收画面、虚拟采集卡输出和下发命令；被采集机只运行采集后台。
产品控制端口固定为 **5143**，不更改机器本身的网卡 IP。旧 18080 部署需要更新并重启，两端应使用同一份新代码。

## 启动

- 主机：便携包双击 `Start-VirtualCapture.cmd`，浏览器打开 `http://127.0.0.1:5143/ui`。源码可运行 `powershell -NoProfile -ExecutionPolicy Bypass -File scripts/start-host.ps1`。
- 被采集机：当前登录桌面用户双击 `Start-Capture-Worker.cmd`；源码可运行 `powershell -NoProfile -ExecutionPolicy Bypass -File scripts/start-capture-worker.ps1`。脚本隐藏启动后台并避免重复进程。也可直接运行 `vc-agent.exe --role capture` 或 `python agent/vc-agent.py --role capture`。
- 被采集机不打开浏览器，也无需填写对端地址、角色或网卡；其 `/ui` 返回 404。采集仅在主机发出命令后启动。
- DDA 后台须在被采集机的登录桌面会话内运行。主机须与下游软件使用同一 Windows 用户，以便读取 HKCU 虚拟采集卡注册。`install-pc2.ps1` 的历史 SYSTEM 计划任务流程不适合直接用于这两种桌面会话要求。

启动器校验已有 5143 服务的角色、能力与运行目录，同目录同角色直接复用；冲突时给出明确错误。源码与成品入口相同，主机脚本可加 `-NoBrowser`；启动日志保存至运行目录的 `run/agent-*.stdout.log|stderr.log`。

## 连接配置

1. 只填写**被采集机 IP**，例如 `192.168.2.59`；不带 `http://` 或端口，实际连接使用 `http://192.168.2.59:5143`。
2. 页面自动获取本机网卡列表，从下拉框选择连接被采集机的网口；“刷新网卡”可重新获取。列表显示网卡名称、描述和状态，不启动采集。
3. 按需选择分辨率预设（416、640、720p、1080p、1440p）或自定义偶数宽高，再选裁切/缩放、帧率、raw/MJPEG。开发版 Raw 已支持这些尺寸与四种变换；MJPEG 为开发模式：明确启用、两端为 `turbojpeg:cpu`、设置 JPEG 质量后才允许启动；缺少后端或协商失败明确拒绝。H.264/H.265 已于 2026-11-13 按 D23 移除，界面不再提供。稳定成品不自动更新。
4. 查看自动计算的链路预算；“重新检测两端链路”可跳过 10 秒探测缓存。预算不保存草稿、不启动采集，也不自动降低分辨率/帧率或切换编码。

画面来源、像素转换、发送批大小和链路 MTU 仍不在页面提供设置，沿用后台配置（新配置默认桌面 DDA、GPU 转换、batch 69、MTU 9000）；保存连接信息不会重置这些参数。旧配置读取后默认仍为 640×640，而不是自动改成第一项 416。

主机角色固定为接收端。共享内存固定为 `Local\VirtualCaptureVcamFrame`，不显示给用户；虚拟采集卡注册和回收自动完成。
没有对端控制台跳转、手动注册或角色选项。网卡名使用实际 Npcap 设备名保存，不需要手写描述子串。
被采集机启动时，根据到主机控制连接的本机出站 IP 精确匹配网卡；匹配不唯一会报错，不会随意选择第一张网卡。
主机能读取所选网卡 MAC 时自动将其用于对端单播；无法读取时使用配置中保留的目标 MAC（默认广播）。

配置存在主机 ROOT 下的 `vc-config.json`。编辑不被轮询覆盖，支持撤销；正在采集时先停止再修改。
旧 IPv4 URL 配置读取时迁移到 5143；旧角色、手动注册开关和自定义 SHM 在产品模式下由固定值覆盖。
底层诊断 API 及显式测试端口仍保留，产品 UI 不暴露这些选项。

编码参数与日志说明见skill `references/encoded-stream.md`；GUI区分Raw像素对账、压缩字节校验和解码状态。PC2后端/双机/长稳/画质未验收，勿直接覆盖稳定版。

## 开始与停止采集

总览只保留**一个采集控制按钮**：就绪时为“开始采集”，运行中或还有待回收资源时为“停止采集”。

- 开始：拒绝尚未接通的流配置 → 检查后台能力、角色和版本及新鲜链路预算 → 注册主机虚拟采集卡 → 启动本机接收 → 下发参数让后台采集并推送。
- 停止：先通知被采集机停止推送，再停止本机接收，注销虚拟采集卡。对端失联也继续清理本机，操作记录报告各端结果。
- 注册未完成、接收启动失败或对端启动失败时回滚；接收进程异常退出由后台每秒检查并回收。回收失败保留资源状态，可重试停止。
- 回收只针对本目录匹配的 DLL。注销不会强制关闭下游软件已经持有的 COM 实例，下次采集可能需要在下游重新选择设备。

主机正常退出会停止本机接收并回收虚拟卡；强制结束进程或断电不保证清理。产品模式缺少原生程序会直接报错，不把占位进程当作有效传输。

## 预算与支持状态

- 输出宽高指传输/虚拟卡目标尺寸，不是修改被采集机桌面显示分辨率。自定义软件参数范围 2..8192 的偶数宽高，不等于管线或 GPU 支持该上限。
- 居中裁切保留 1:1 像素；完整画面模式规划为等比缩放加黑边，铺满模式为等比缩放后裁切，拉伸模式不保持比例。四种均已在开发版接通；整数最近邻采样，黑边Y=0/UV=128。源小于目标时1:1裁切明确拒绝，可主动选择缩放。
- 按实际所选主机网卡接收速率与采集后台控制路由网卡发送速率取较慢者；信息缺失显示未知，不假定两端都是 2.5G。旧采集后台缺P6-2显式会话接口时拒绝启动，不自动升级或重启。
- Raw 预算包括 NV12、分包头、FCS、前导码及帧间隙，默认预留 20%；这只是预算余量，不是放宽性能验收。超物理线速或网卡断开拒绝启动，侵入余量只建议调整。
- MJPEG 带宽按最大码率均摊估算，不保证单帧瞬时突发、编码吞吐或画质；开发模式会核对两端后端并实际协商，协商不是实帧验收。最大码率由发送起点一秒滑窗约束，可能降低实际输出频率；JPEG 质量固定，不按目标码率做 CBR。Raw 路径独立保留。
- 开发版 DDA 按新图像驱动且受真正发送帧率上限约束，发送开始间隔至少ceil(1e9/fps) ns；合并中间更新、不FIFO追赶，静态桌面不重复发送。上限不是实际帧率承诺。
- “预算可容纳”“原生已实现”“实机验收通过”是不同结论，不能相互替代。稳定部署不自动替换，本轮先在隔离环境开发验证。

## 指标与排障

- 离线、停止、缺少指标或测试桩进程显示 `—`，真实零值显示 `0`；断线后自动重连。帧率在换会话、计数回退和长时间失联后重建基线。
- 产品启动会检查原生进程是否在约 1 秒内提前退出，失败返回日志并回滚；后续异常退出也会显示错误。两端进程已启动但 complete=0 时显示“等待首个完整画面”；采集方式使用实际会话参数。
- 延迟曲线显示最近 60 秒各段 p99，分段在各自机器内测量，不跨机比较 QPC；UI 不是完整双机验收判定器。
- “请更新被采集机后台”：两端源码/能力不匹配，或对端未用 `--role capture` 启动。新主机需要 `/health` 的 `product_revision=2`、`stream_revision=2`、`product_role=capture`，还会探测真实原生程序，不能只更新Python。
- “等待采集后台上线”：检查 IP、5143 监听和该网口的网络连通性；程序不会自动改变网卡 IP 或防火墙规则。
- 预览画面继续用 `vc-monitor.exe`（同一共享内存）；下游软件选择 `VirtualCapture`。先开始接收再打开下游；改变尺寸/fps时先关闭下游设备再停止/重启采集，然后重新打开，DShow格式在实例创建时固定。同名SHM仍被旧下游/预览持有会明确拒绝重开，不会覆盖旧映射。
- 产品会话 frames 0 / timeout 0；hashlog 每小时约 60MB/端，长期运行留意 `run/` 空间。
- 操作记录只保留当前页面最近 80 条；清空显示不删除服务端证据。更新源码后重启对应 agent；发版按现有打包/OTA 流程。
